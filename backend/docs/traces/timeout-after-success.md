# End-to-end trace: a booking that times out *after* succeeding

Raw file: [`timeout-after-success.json`](timeout-after-success.json) (3 runs, 21 spans). Generated by
`PYTHONPATH=. uv run python scripts/make_trace.py` against the real OpenAI model and the mock providers
(Tuesday is the day `book` times out even though the booking went through). Same spans are in LangSmith when tracing is on.

User: *"Fan regulator is broken, I need an electrician in Indiranagar tomorrow evening, under 1500."*
→ taps *Amit Electricals, Tue 3 Nov, 6–8 pm* → taps **Approve**.

## Annotated excerpt (the Approve run, `turns=0`, `tool_calls=0`)

| # | Span | What it shows |
|---|---|---|
| 0 | `approval: approved` | The user's button, verified by code. The approval (`bff735fd…`) is hash-bound and now consumed: it cannot be used twice. |
| 1 | `state: AWAIT_APPROVAL → EXECUTE` | From here **no model is involved**. This run has no `model_call` span at all. |
| 2 | `tool_call: exec.book` **`error: ToolTimeout`** | The side effect. Idempotency key `idem_bff735fd…` is derived from the approval id, and the attempt row was written *before* this call (write-ahead). The call timed out: **the outcome is unknown**. |
| 3 | `state: EXECUTE → RECONCILE` | The executor does not retry blindly and does not say "booked". It goes to the source of truth. |
| 4 | `tool_call: exec.get_booking_status` → `booked`, `bk_6d4fd50d`, ₹1250 | Asked by hold id. The provider says the booking **did** happen, with the slot and price matching the card. |
| 5 | `tool_call: exec.get_booking_status` → `booked`, same booking | Asked again by idempotency key. Same answer (a second, harmless confirmation). |
| 6 | `state: RECONCILE → DONE` | Only now is success claimed: *"Booked and verified: electrician with Amit Electricals, Tue 3 Nov, 6–8 pm, ₹1250."* |

## What to notice

- **The timeout did not cause a second booking.** `retry_count: 0`, one attempt, one booking
  (`proof_one_booking_one_attempt` at the bottom of the JSON). A blind retry would have used the same key anyway,
  so the provider would have replayed the first result instead of double booking.
- **Success is verified, not assumed.** The message comes after `get_booking_status`, never after the timeout.
- **The model never touched the money step.** Run 1 (the slot tap) and run 2 (Approve) both have `turns=0`: no model call.
  The only model calls are in run 0 (understanding the request, the answer, the title, and one memory pass).
- **Everything before the booking is visible too:** run 0 shows the memory pass saving the area
  (`memory_saved: preferred_area`, with the user's own words as evidence), the context build (2,837 tokens against a
  6,000 budget), the search inside `update_request_frame`, and each model call's latency and token counts.
- **Honest detail:** span 5 is a redundant second status call (by hold id, then by key). It is harmless, both agree,
  and is a candidate for removal.
